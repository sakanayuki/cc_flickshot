### 0.3 ルールの全面見直し(2026-07-28)

当初は「下から上へ登る」ゲームとして実装していたが、発注者の意図した実機は
**「上から下へ降りる」**ゲームだった。以下がすべて反転している。

| | 旧(やまのぼり) | 新(やまくだり) |
|---|---|---|
| 進む向き | 下 → 上 | **上 → 下** |
| 投入位置 | 左下 | **右上** |
| 弾く向き | 斜め上(仰角26°) | **ほぼ横**(仰角12°。→ 後に §0.35 で 28° に戻した) |
| 強すぎたとき | 天井に当たって減速、失敗しない | **奥の穴に落ちて没収** |
| 弱すぎたとき | 同じ段に戻る | **手前の穴に落ちて没収** |
| クリア | 山頂のゴールバスケット | **最下段の下のあたりの口** |
| 難易度差 | 穴の数・半径・落下閾値・ゴール幅・リップ高の5つ | **板の幅だけ** |
| 盤面の高さ | 画面の 55% | **画面の 74%** |
| プランジャー帯 | 画面の 41%(指ストローク450px) | **画面の 22%**(指ストローク240px) |

旧ルール固有の仕組み(上向きシャフト、レーン先端・裏面の当たり判定、リップ越えの転落、
転がり速度による穴判定、壁での跳ね返り)は**すべて削除した**。

### 0.35 盤面の作り直し(2026-07-28(4))— 貫通の原因と対処

**発注者から「棒を貫通する」との指摘があった。これはチューニングでは直せない
構造的な欠陥だったため、盤面の幾何と衝突判定を作り直した。**

旧設計は「溝は板の低い**側**」「弾く向きは**溝と反対**」だった。
つまりコインは自分が乗っている板の上を逆走する形で飛び出す。
板は飛行方向に向かってせり上がっているので、**どんな弾道でも板の内部を通る**。
さらに着地判定を「1段下の板だけ」に限っていたため、自分の板との衝突が
そもそも計算されず、コインが板をすり抜けて見えていた。

| | 旧 | 新 |
|---|---|---|
| 板の並び | 中央を挟んで左右にずらす | **ジグザグ**(溝が中央の隙間を挟んで向かい合う) |
| 溝の位置 | 板の低い「側」 | 板の**先端** |
| 弾く向き | 溝と反対(=自分の板の上を逆走) | **先端の外**(自分の板から離れる) |
| 衝突対象 | 1段下の板の上面だけ | **全ての板の実体**(上面+厚み+端面) |
| 積分 | 1フレーム1回 | **1サブステップ 6px 以下に分割** |
| 端に当たったとき | 判定なし | 水平の勢いを失ってそのまま落ちる(跳ね返さない) |
| 穴 | 「板でないところ」の帯 | **丸い落とし穴**(実機と同じオレンジのリム付き) |
| 仰角 | 12° | **28°** |

新しい幾何では、溝から弾いたコインは即座に板の外へ出る。
**自分の板を横切ることが構造的にありえない**ので、貫通は幾何のレベルで消えている。
その上で全板との実体衝突を持たせ、検算 §12-7 が全パワー掃引で担保する。

### 0.36 弾く点を画面の端へ(2026-07-31)— レーンの作り直し

**発注者から実機の写真とともに2点の指摘があった。**

1. レーンを写真の青い線のように引き直すこと。丸くなっているところは穴で、入ればアウト
2. 弾く点が画面中央付近にある。写真のように、**レーンが左右の画面端に接するところの
   横のレバー**で弾く形にすること(プランジャー1操作という仕様はそのまま)

§0.35 の設計は「溝から**板の外**へ弾く」ことで貫通を消していたが、その代償として
弾く点は盤面の中央付近に固定されていた(§3.0.1 の綱引き)。指摘の 2 を満たすには
この前提そのものを裏返すしかない。

| | 前(§0.35) | 現在 |
|---|---|---|
| 先端(弾く点)の位置 | 中央の隙間の両縁(x=230 / 490) | **左右の壁ぎわ(x=124 / 596)** |
| レールの並び | 中央を挟んで向かい合う2本の柱 | **左端・右端・左端…と交互** |
| 弾く向き | 先端の外(板から離れる) | **盤面の内側(自分のレールを飛び越す)** |
| レバーの位置 | 先端の真下 | **先端の横、壁から生える**(写真と同じ) |
| 手前の穴 | 2本の柱の間 | **盤面の中央**(丸を並べて開口を埋める) |
| 奥の穴 | 板の高い端 〜 壁 | **先端 〜 壁(`TIP_INSET`)** |
| 仰角 | 28° | **35°** |
| 板の幅(易/普) | 120 / 80 | **140 / 100** |
| 弾き力 | 530..840 | **665..950** |

自分のレールを飛び越す弾道は、§0.35 が消したはずの貫通が戻ってくる形でもある。
今回はそれを**幾何で消すのではなく、成立条件として明文化して機械で守る**:

- 仰角ぶんの上昇がレールの傾きぶんの上昇を全長にわたって上回ること
  → 下限が `FLICK_RISE` / `P_MIN`、上限が `plankWidth` / `PLANK_DROP`
- 頂点が高くなりすぎて 1 段上のレールの裏に当たらないこと
  → 上限が `FLICK_RISE` / `P_MAX`
- 高い端の返し(旧 `PLANK_LIP`)は**廃止**。返しがあると飛び越せない。
  着地したコインは必ず先端側へ転がるので、返しはもともと不要だった

前者2つは検算 §12-8 が、物理エンジンを通さない理想の放物線で直接測る。
エンジンの押し出しに隠されて「当たっているのに検算は通る」状態を防ぐため、
§12-7(実物理の掃引)とは別に持っている。現在の余裕は最小 14px(コイン半径の半分)。

### 0.37 コインは飛ばない。レーンの上を走る(2026-07-31(2))

**発注者から、弾いたあとの動きが違うとの指摘があった。**

> 弾く機能は、玉が飛ぶというより、勢いがついてレーンの上を沿って走るイメージです。
> この青レーンを再現するように忠実にしてください

§0.36 までは放物線で飛ばす設計だったため、盤面は**切れ切れのレール**の集まりに
ならざるをえず、写真の青い線のような「1 本につながったレーン」にできなかった。
物理そのものを置き換えた。

| | 前(§0.36) | 現在 |
|---|---|---|
| コインの動き | 放物線で飛ぶ(2次元) | **レーンに沿って走る(1次元)** |
| 状態 | `onPlank` / `airborne` / `falling` / `win` | **`onLane` / `falling` / `win`** |
| 位置・速度 | `pos: Vec2` と `vel: Vec2` | **経路上の距離 `s` と前向きの速さ `v`** |
| 盤面 | 切れ切れのレール 5 本 | **1 本につながった折れ線**(直線 + 壁でのUターン) |
| 弾く | 仰角つきの初速 | レーンに沿った初速。**仰角という概念が消えた** |
| 止まる場所 | レールの先端の溝 | 走路の端(画面の左右の端)の**止まり木** |
| 穴 | レールとレールの隙間 | **レーンの床に開いた丸い口**(Uターンを出てすぐ) |
| 弱すぎ | 隙間を飛び越せない | **穴の上で勢いを失って落ちる** |
| 強すぎ | 板を飛び越して奥の穴 | **止まり木を乗り越えて**その先の穴へ |
| 難易度差 | 板の長さ | **穴の長さ** |
| 当たり判定 | 全レールの実体(上面+厚み+端面) | **不要**(1次元なので貫通も場外も起きない) |

弾く点が画面の左右の端にあること(§0.36 の要望)と、プランジャー 1 操作で
全レバーが連動する仕様はそのまま維持している。

**消えた不具合と、新しく生まれた不具合の芽。**
1 次元にしたことで「板を貫通する」(§0.35)と「盤面の外に出る」は**原理的に**消えた。
検算 §12-7/§12-8 の弾道チェックも役目を終えて撤去した。
代わりに**「コインがレーンの途中で完全に止まって詰む」**が起こりうる。
弾くこともできず結果も出ないので、進行不能になる。

レーンにわずかな傾き `LANE_ASSIST` を持たせ、止まりかけたコインをゆっくり
前へ送り続けることで潰した。止まりかけの速さ `LANE_CREEP = LANE_ASSIST / LANE_DRAG`
は穴に必ず捕まる速さ(`< HOLE_CATCH_SPEED`)にしてあるので、
「穴の手前で永久に静止する」も起きない。検算 §12-5 が全パワーで確認する。

### 0.38 レーンはななめ上向き。コインは登る(2026-07-31(3))

**発注者から、作っているものが実機と違うとの指摘があった。**

> 筒みたいな全然違うゲームになってる。
> ○重力は画面下向きに働いている
> ○レーンがななめ上向きにある
> ○バーを弾くことでコインに勢いがつき、このレーンを登ることができる。
> ○勢いが強すぎたり弱すぎるとアウトになるような、レーンに隙間や穴がある。
>   適切な力で弾いたときの隙間から落ちたときだけ下の段に進める

§0.37 は「1 本につながったレーンを走る」形にしたが、これはレーンをつないで
**筒のように**してしまい、実機の「段になったななめのレーンを登り、隙間から落ちて
下の段へ移る」構造とは別物だった。重力も画面下向きには効いておらず、
進行方向の摩擦として扱っていた。

| | 前(§0.37) | 現在 |
|---|---|---|
| 重力 | 進行方向の摩擦 `LANE_DRAG` | **画面の下向き。斜面の減速は `GRAVITY * sinθ`** |
| レーン | U ターンでつながった 1 本 | **ななめ上向きのレーンが 5 段**(つながっていない) |
| 弾いたあと | 走って減速し止まり木で止まる | **レーンを登る**。登りきれなければ滑り降りてくる |
| 段の移り方 | U ターンを回って次の走路へ | **隙間から落ちて 1 段下のレーンへ** |
| 状態 | `onLane` / `falling` / `win` | **`onLane` / `dropping` / `lost` / `win`** |
| 位置 | 経路上の距離 `s` | **斜面に沿った距離 `u`**(落下中だけ 2 次元) |
| 弱すぎ | 穴を渡りきれない | **手前の穴**を渡りきれない |
| ちょうど | 止まり木に受け止められる | **隙間から落ちて次の段へ**(発注者の指摘の芯) |
| 強すぎ | 止まり木を乗り越える | **隙間を飛び越して奥の穴**へ |
| 難易度差 | 穴の長さ | **手前の穴の長さ** |

レバーが画面の左右の端にあること(§0.36)と、プランジャー 1 操作で全レバーが
連動する仕様はそのまま維持している。

**摩擦を入れないことにした。** 斜面に摩擦を入れると登りと下りが非対称になり、
挙動が読みにくくなる。摩擦なしの等加速度にすると、成功する初速が閉じた式で書ける
(§4.4)。チューニングはこの式で当たりをつけ、**式と実物理が一致すること自体を
検算に入れた**(§12-3)。片方だけ壊れても気づける。

**新しく生まれた失敗の芽は 2 つ。**

1. *着地したコインが自分から手前の穴に落ちる。*
   隙間から落ちたコインは 1 段下のレーンに乗って滑り降りるので、着地点が
   手前の穴より奥だと途中で落ちてしまう。**隙間をレーンの高い端の側に置く**ことで、
   着地点が必ず低い端の側に来るようにした(§3.2)。検算 §12-1 が数値で固定する。
2. *弾いても何も起きない「空振り」。*
   手前の穴に届かない弱さで弾くと、コインは滑り降りてレバーに戻るだけになる。
   3歳児には理由が分からないので、`P_MIN` を「最弱でも手前の穴には必ず届く」値より
   上に置いた。検算 §12-3 / §12-5 が空振り 0 件を確認する。

### 0.4 設計の中心にある考え方

1. **5回の操作をすべて同一条件にする。**
   レーンを**すべて同じ形(左右反転のみ)**で作るので、斜面の長さも傾きも
   穴と隙間の位置も 5 段すべてで完全に一致する。
   チューニング定数は `P_MIN` / `P_MAX` の2つで済み、
   3歳児は「同じ引き方」を5回繰り返せばよい。
2. **摩擦を入れない。**
   斜面の加速度は `-GRAVITY * sinθ` だけ。登りと下りが対称になり、
   成功する初速が閉じた式で書ける(§4.4)。式と実物理の一致を検算で担保する。
3. **失敗は必ず両側にある。**
   弱すぎ → 手前の穴、強すぎ → 隙間を飛び越して奥の穴。
   片側しか失敗しない配置は設計が崩れている証拠なので、検算スクリプトが自動で落とす。
4. **時間的な制約を作らない。**
   コインは必ずレバーで止まる。
   3歳児が落ち着いてプランジャーを引ける時間を無制限に確保する。
5. **跳ね返らせない。**
   跳ね返ると「強すぎたのに戻ってきて助かる」が起き、*強すぎ = 失敗* が崩れる。
6. **空振りを作らない。**
   弾いたのに何も起きずレバーに戻るパワー帯があると、3歳児には理由が分からない。
   `P_MIN` は「最弱でも手前の穴には必ず届く」値より上に置く(§0.38)。

## 1. 全体アーキテクチャ

### 1.1 依存方向

```
main.ts
 ├─ scenes/{title,game,result}.ts
 │    ├─ game/{board,coin,plunger,levers}.ts   ← Canvas / DOM を一切参照しない
 │    ├─ render/{layout,drawings,shapes,animals,particles}.ts
 │    └─ save.ts
 └─ config.ts                                  ← 副作用のない葉ノード
```

**`src/game/` は Canvas も DOM も参照しない。** Vitest でそのままテストできることが要件。
`scripts/verify-geometry.ts` も同じ理由で `src/game/` を直接 import して実物理を回す。

### 1.2 メインループ

```
frame(nowMs):
  acc += min(now - prev, MAX_FRAME_TIME)   // タブ復帰時のスパイラル防止
  applyPendingTransition()
  while acc >= FIXED_DT:
    current.update(FIXED_DT)               // 物理には常に固定 dt
    acc -= FIXED_DT
    if pending: applyPendingTransition(); acc = 0; break
  try:
    clearFull(); applyTransform(); current.render()
  catch err:
    crashed = true; showFatal(err)         // 真っ青画面の再発防止(§0.5)
  requestAnimationFrame(frame)
```

- シーン遷移は `update` の途中では行わず、次フレームの先頭で差し替える。
- 現在のシーン名を `document.body.dataset.scene` に出す。自動テストから遷移を観測するためだけのもの。

### 1.3 起動失敗を必ず見せる

JSが読み込めなかった/描画で例外が出たときに、body の背景色だけが見える
**「真っ青な画面」**になると端末側からは原因が全く分からない。以下を必ず持つこと。

- `window.onerror` / `unhandledrejection` → `showFatal()` で画面に理由を表示
- 描画ループの try/catch → 同上
- `index.html` に `<noscript>`
- `vite.config.ts` は `base: './'`(相対パス)

## 2. 座標系とレイアウト

### 2.1 論理座標系

**720 × 1280(9:16 縦)**。全シーンこの座標系で描画する。

### 2.2 実画面へのフィット

```ts
scale   = min(cssW / 720, cssH / 1280)
offsetX = (cssW - 720 * scale) / 2
offsetY = (cssH - 1280 * scale) / 2
dpr     = min(devicePixelRatio, MAX_DPR = 3)
canvas.width  = round(cssW * dpr)
canvas.height = round(cssH * dpr)
ctx.setTransform(dpr*scale, 0, 0, dpr*scale, dpr*offsetX, dpr*offsetY)
```

- レターボックスの余白は `clearFull()` で空色に塗る。
- ポインタ座標は `toLogical()` で必ず論理座標に変換してからシーンに渡す。
- `resize` / `orientationchange` で再計算する。

### 2.3 ゲーム画面の領域割り(720×1280)

| 領域 | 範囲 | 画面比 |
|---|---|---|
| 盤面 | y 40 .. 994 | **74%** |
| プランジャー帯 | y 994 .. 1280(286px) | **22%** |
| 盤面の壁 | x 40 .. 680 | — |

- ノブ中心 (560, 1040)、半径 46。`KNOB_REST.y - KNOB_R = 994` なので盤面と重ならない。
- 指のストローク 240px。`1280 - 1040 = 240` でちょうど画面下端まで届く。
- ノブの見た目の移動量 190px。`1040 + 190 + 46 = 1276 ≤ 1280` で画面内に残る。
- 掴み領域は帯のほぼ全体 `{x: 300, y: 996, w: 420, h: 284}`。

## 3. レーンの幾何

### 3.0 全体像

```
              [投入口]
 段1:  ●●●━┈┈┈━○○━━━━━━━━●    ← 低い端は右。左上へ登る
            ↓ 隙間から落ちる
 段2:  ●━━━━━━━━○○━┈┈┈━●●●    ← 低い端は左。右上へ登る
                      ↓
 段3:  ●●●━┈┈┈━○○━━━━━━━━●
            ↓
 段4:  ●━━━━━━━━○○━┈┈┈━●●●
                      ↓
 段5:  ●●●━┈┈┈━○○━━━━━━━━●
            ↓
       [あたりの口]
```

- `●`(低い端)= レバー。コインはここで止まり、ここから弾く
- `○○` = 手前の穴(弱すぎ) / `┈┈` = 隙間(ここから落ちて次の段へ) / `●●●` = 奥の穴(強すぎ)

**重力は画面の下向きに働く。** レーンはななめ上向きなので、コインは低い端まで
滑り降りて止まる。弾かれると斜面を登り、`GRAVITY * sinθ` で減速していく。

### 3.1 1 本のレーン

```ts
LANE_INSET   = 68                       // 壁からレーンの端まで
LANE_LEFT_X  = 40 + 68  = 108
LANE_RIGHT_X = 680 - 68 = 612
LANE_SPAN_X  = 504                      // 水平距離
LANE_RISE    = 60                       // 高低差。低い端 → 高い端でこれだけ登る
length       = √(504² + 60²) = 507.6    // 斜面の長さ
decel        = GRAVITY * 60 / 507.6 = 260 px/s²   // = GRAVITY * sinθ
```

- 低い端は壁ぎわ(壁から 68px)。**段ごとに右・左・右…と交互**なので、
  レバーも左右交互に並ぶ(実機の写真と同じ)。
- 傾きは約 7°。実機の写真のレーンもゆるい傾きなので、見た目としても近い。

> **`LANE_RISE` の上限は「段どうしが重ならないこと」で決まる。**
> `ROW_GAP > LANE_RISE + レーンの太さ(LANE_W + LANE_RAIL*2)` を満たすこと。
> 現在は `136 > 60 + 74 = 134` で 2px の余裕しかない。傾きを強めたいときは
> `ROW_GAP` を広げるか段数を減らすしかない。

### 3.2 穴と隙間の配置 — 5回の操作を同一条件にする

低い端からの距離 `u` で、全段まったく同じ位置に置く。

| 区間 | u | 役割 |
|---|---|---|
| 実線 | 0 .. 230 | 1 段上から落ちてきたコインが滑り降りてくる区間 |
| **手前の穴** | 230 .. 230+`nearHoleSpan` | 渡りきれないと落ちる(**弱すぎ**) |
| 実線 | +20 (`GAP_LEAD_U`) | |
| **隙間** | .. 440 (`GAP_END_U`) | **ここから落ちると 1 段下へ進める** |
| **奥の穴** | 440 .. 507.6 | 隙間を飛び越すと落ちる(**強すぎ**) |

**隙間はレーンの高い端の側に置く。** これが効いているのは次のためで、外すと壊れる。

隙間から落ちたコインは真下に落ちるので、1 段下のレーン(左右反転)では
`u' = length - u` の位置に着地する。隙間が高い端の側にあれば `u'` は低い端の側になり、
着地したコインは**手前の穴を通らずに**レバーまで滑り降りられる。

```
着地 u' の範囲 = length - 隙間の範囲
  やさしい: 67.6 .. 197.6      ← どちらも HOLE_NEAR_U = 230 より小さい
  ふつう  : 67.6 .. 127.6
```

検算 §12-1 と Vitest がこの不等式を数値で固定している。

### 3.3 難易度別の実測値

| | やさしい (手前の穴 60) | ふつう (手前の穴 130) |
|---|---|---|
| 手前の穴 | 230 .. 290 | 230 .. 360 |
| 隙間 | 310 .. 440(130 幅) | 380 .. 440(60 幅) |
| 奥の穴 | 440 .. 507.6 | 440 .. 507.6 |
| 着地 u | 67.6 .. 197.6 | 67.6 .. 127.6 |
| 成功する初速 | 436.8 .. 518.5 px/s | 476.7 .. 518.5 px/s |

**手前の穴が短いほど、渡りきるのに要る勢いが小さくて済み、隙間も広くなる。**
上限と下限の両方が効くので、易しさの差が素直に出る。

### 3.4 あたりの口

最下段の隙間の**真下**に、隙間と同じ幅で置く。落ちてきたコインをそのまま受けるので、
6 回目の操作も他とまったく同じ条件になる。

### 3.5 段の縦の配置

```ts
ROW_TOP_Y = 248     // 1 段目の低い端の y
ROW_GAP   = 136     // 低い端どうしの間隔
ROW_COUNT = 5
あたりの口の y = 248 + 4*136 + 136 = 928   （+52 の受け皿を入れて 980 < 994）
```

## 4. 物理モデル

### 4.1 コインの状態機械

```ts
type CoinState = 'onLane' | 'dropping' | 'lost' | 'win'

interface Coin {
  state: CoinState;
  laneIndex: number;  // いま乗っている(または向かっている)段
  u: number;          // onLane: 斜面に沿った位置。低い端が 0
  v: number;          // onLane: 斜面に沿った速さ。登りが +
  held: boolean;      // レバーで静止中。true のときだけ弾ける
  pos: Vec2;          // 描画用
  vel: Vec2;          // dropping のときの速度
  timer: number;      // lost / win の演出経過秒
  lostKind: 'weak' | 'strong' | null;
  lostAt: Vec2;       // 落ちた穴の中心(演出の吸い込み先)
  spin: number;
}
```

### 4.2 `onLane` の更新 — 斜面に沿った 1 次元

```ts
steps = clamp(ceil(|v| * dt / MAX_SUBSTEP_MOVE), 1, 24)
h     = dt / steps

for s in 0..steps-1:
  v -= lane.decel * h        // 斜面に沿った重力。つねに低い端の向き。摩擦は無い
  u += v * h

  if |v| < HOLE_CATCH_SPEED:            // 勢いがあれば口をかすめて渡れる
    if u が隙間の中     → dropping へ（**成功。1 段下へ**）
    if u が手前の穴の中 → lost 'weak'
    if u が奥の穴の中   → lost 'strong'
  if u > lane.length → lost 'strong'    // 高い端を越えた
  if u <= 0 → u=0, v=0, held=true       // レバーで受け止める
```

**摩擦を入れない**ので、登りきれなかったコインは必ず同じ速さで滑り降りてくる。
「レーンの途中で永久に止まる」は起こらない。

### 4.3 `dropping` の更新 — 画面下向きの自由落下

隙間から落ちた瞬間の速度は 0 にして、そこから `GRAVITY` で素直に落とす。
真下に落ちるので、着地点は隙間の x そのままになり、§3.2 の不等式が効く。

1 段下のレーンの上面 `laneYAtX` を下向きに横切ったら着地。
斜面に沿った成分だけを引き継いで `onLane` に戻る(必ず低い端へ滑り出す)。
最下段なら、あたりの口の高さに達した時点で `win`。

### 4.4 成功の条件 — 閉じた式で書ける

摩擦なしの等加速度なので `v² = v0² - 2 * decel * u`。したがって

| 条件 | 式 | 破ると |
|---|---|---|
| 手前の穴を渡りきる | `v0² >= C² + 2·decel·nearHole.to` | **弱すぎ** |
| 隙間で落ちる | `v0² <  C² + 2·decel·gap.to` | **強すぎ**(奥の穴へ) |

(`C` = `HOLE_CATCH_SPEED` = 200)

この 2 つが `successPowerBand()` の中身で、チューニングの出発点になる。
**式と実物理が一致していること自体を検算 §12-3 でテストしている。**
片方だけ壊れても気づけるようにするため。

> 手前の穴を渡りきったコインは、必ず隙間まで届く。
> 渡りきった時点で `v² >= C² = 40000` あり、あと `C²/(2·decel) = 77px` 登れるので、
> `GAP_LEAD_U = 20` を必ず越える。だから「穴は渡ったが隙間に届かず落ちてくる」
> という中途半端な結果は起こらない。

### 4.5 `lost` / `win`

どちらも `timer += dt` するだけの演出状態。物理は止まる。

- `lost`: `FALL_ANIM = 1.0` 秒。穴の口まで滑る → 沈みながら縮小 → フェード。
  沈み始めたら**穴の手前側のリムをコインの上に重ねて描く**(`drawHoleFront`)。
- `win`: `WIN_ANIM = 1.5` 秒。あたりの口の中で小さく跳ねる。

## 5. 難易度

### 5.1 パラメータ

```ts
DIFFICULTIES = {
  easy:   { id: 'easy',   label: 'やさしい', nearHoleSpan: 60 },
  normal: { id: 'normal', label: 'ふつう',   nearHoleSpan: 130 },
}
```

**難易度差は手前の穴の長さだけ。** 弾き力の範囲・ストローク・レーンの形・
レバーの位置はすべて共通。穴が短いほど

- 渡りきるのに要る勢いが小さい(下限が下がる)
- そのぶん隙間が広い(上限は同じなので、成功域が広がる)

の両方が効く。難易度を切り替えても弾く点も指の感覚も変わらない。

### 5.2 実測された成功域(`npm run verify`)

| 操作 | やさしい | ふつう |
|---|---|---|
| 段1 → 段2 | 63%(pull 0.27〜0.86) | 32%(pull 0.56〜0.86) |
| 段2 → 段3 | 63% | 32% |
| 段3 → 段4 | 63% | 32% |
| 段4 → 段5 | 63% | 32% |
| 段5 → あたりの口 | 63% | 32% |

- すべて**連続した1区間**。飛び地はない。
- すべての操作で**弱すぎ・強すぎの両方の失敗が存在する**。
- **空振り(弾いてもレバーに戻るだけ)が 0 件。**
- **5段とも数値が完全に一致している。** レーンが同じ形なので構造的にそうなる。

### 5.3 P_MIN / P_MAX の決め方

手で決めてはいけない。**`successPowerBand()` の閉じた式で境界を出してから逆算する。**

```
a  = 成功する初速の下限(やさしい)   = √(C² + 2·decel·290) = 436.8
a' = 成功する初速の下限(ふつう)     = √(C² + 2·decel·360) = 476.7
b  = 成功する初速の上限(難易度共通) = √(C² + 2·decel·440) = 518.5

やさしいの成功域を目標比 f に置く:
  実効range = (b - a) / f
  弱すぎ区間と強すぎ区間で残りを分け合う
  P_MIN は pull = PULL_DEADZONE のときに弱すぎ側へ届く値にする
```

現在値は `P_MIN = 402` / `P_MAX = 537`。デッドゾーンを除いた実効範囲は 408.8..537。

**下限にはもう 1 つ条件がある。** 「最弱でも手前の穴には必ず届く」こと。

```
√(2·decel·nearHole.from) = √(2·260·230) = 345.8  <  408.8
```

これを割ると、弾いてもコインが滑り降りてレバーに戻るだけの**空振り**が生まれる
(§0.38)。検算 §12-5 が固定している。

### 5.4 チューニングの経緯(再発防止のため記録)

| 試した値 | 結果 | 判断 |
|---|---|---|
| コインを放物線で飛ばす(§0.35〜§0.36) | 盤面が切れ切れのレールになる | 却下(§0.37) |
| 1 本につながったレーンを走らせる(§0.37) | **筒のようになり、実機の「段を登る」構造と別物** | 却下(§0.38) |
| 斜面に摩擦を入れる | 登りと下りが非対称になり、閉じた式が書けない | 却下。摩擦なしにした |
| 隙間をレーンの低い端の側に置く | 落ちた先が手前の穴より奥になり、**着地したコインが自分から落ちる** | 却下。高い端の側に置く(§3.2) |
| `LANE_RISE = 110` | 傾きは目立つが、**段どうしが重なって**レーンが読めない | 却下。60 に下げた |
| `P_MIN = 340` | 手前の穴に届かず**空振り**するパワー帯ができる | 却下。402 に上げた |
| `LANE_RISE = 60`、手前の穴 60/130、`P 402..537` | 易 63% / 普 32%、5段とも完全に一致 | **採用** |

手前の穴の上限は「隙間が残ること」で決まる。長くしすぎると
`nearHole.to + GAP_LEAD_U` が `GAP_END_U` を越えて隙間が消え、成功域が無くなる。

## 6. プランジャーとレバー

### 6.1 入力の取り扱い

- Pointer Events のみ(Touch/Mouse を個別実装しない)。
- 掴めたら `canvas.setPointerCapture(pointerId)`。失敗しうる環境があるので try/catch。
- **`pointercancel` でも発射する。** iOS でシステムジェスチャに割り込まれたときに
  操作が無かったことにならないようにするため。
- **横方向の移動は完全に無視する。** 下方向の変位 `dy` だけを見る。
  3歳児のドラッグは大きく蛇行するため、これが「シビアな操作を減らす」要件の実装手段のひとつ。

### 6.2 HTML / CSS 側の必須設定

```html
<meta name="viewport" content="width=device-width, initial-scale=1, user-scalable=no, viewport-fit=cover">
```
```css
canvas { touch-action: none; }
html, body { overscroll-behavior: none; user-select: none; -webkit-user-select: none;
             -webkit-tap-highlight-color: transparent; }
```

### 6.3 ストローク — 指とノブの分離

| | 値 |
|---|---|
| 指の移動量 `STROKE_FINGER` | **240px** |
| ノブの見た目の移動量 `STROKE_KNOB` | **190px** |

指 240px は「盤面を74%にする」要件と両立させた上限
(`LOGICAL_H - KNOB_REST.y = 1280 - 1040 = 240`)。
ノブを 190px にとどめることで、引ききってもノブが画面内に残る。

旧仕様の 450px から縮んだぶんの余裕は、**板を広く取ること**で吸収している(§5)。

### 6.4 `pull` → 弾き力

```ts
pull  = clamp(dy / STROKE_FINGER, 0, 1)
power = P_MIN + (P_MAX - P_MIN) * pull      // 665 .. 950 px/s
if (pull < PULL_DEADZONE = 0.05) → 発射しない(誤タップで空撃ちしない)
```

### 6.5 レバー(ハンマー)

```ts
interface LeverState {
  swing: number;   // -1..0 タメ / 0 静止 / 0..1 はたき(1 が振り上げの頂点)
  timer: number;   // はたきアニメの残り
  flash: number;   // 打撃直後の光 (0..1)
}
```

- 見た目: **レーンの低い端(壁ぎわ)に立つハンマー**(実機の写真と同じ)。
  軸は低い端の外側 `low.x ± 34`、高さ `low.y + LANE_W/2 + 12`。
  斜面の下向きを基準に構え、はたくと斜面の上へ振り上がる。
  軸がコインの外側にあるので、振ると必ずコインを斜面の上へ押し出す形になる。
- 軸は筐体の側面を貫いて丸いノブになる(`drawSideKnobs`)。低い端が右・左・右…と
  交互なので、ノブも左右交互に並ぶ。ロッド(`drawLeverRods`)が壁のノブと軸をつなぐ。
- 引いている間: `swing = -pull`(全段が連動してタメの姿勢になる。視覚フィードバック)
- 発射時 `triggerLevers()`: 全段の `timer = LEVER_SWING_TIME (0.22s)`、`flash = 1`。
  `t < 0.35` で一気に振り上げ、その後戻る。振り上げ中は扇形の残像を描く。
- レバーは**見た目だけ**。当たり判定は `canFlick` / `flickCoin` が持つ。

### 6.6 発射のタイミング — レバーが当たってから動き出す

`pointerup` の瞬間にコインが動き出すと、レバーが振り上がる前にコインが離れて
「はたかれた」ように見えない。そこで発射を `LEVER_HIT_DELAY = 0.06` 秒だけ遅らせる。

```
pointerup → triggerLevers() ですぐレバーが動き出す
          → pendingPower に power を積む
0.06s 後  → flickCoin(power)。同時に打撃点に星を撒く
```

`beginEnding()` は `pendingPower` を破棄する(あきらめた直後に動き出さないように)。

### 6.7 クールダウン

発射後 `FLICK_COOLDOWN = 0.35` 秒は再度掴めない。表示はしない。

```
6  drawLeverRods              ノブとレバーをつなぐロッド(レーンの下を通る)
7  段ごとに drawLane → drawLaneArrows → drawOutHoles → drawGap
8  drawLever × 5              レーンの低い端に立つレバー
9  コイン(状態別)+ drawHoleFront(沈むとき手前のリムを重ねる)
10 particles                  着地の土煙・隙間から落ちる星・あたりの紙吹雪
11 drawBoardFrame             窓枠+ネジ+ガラスの反射。中身を全部覆う
12 drawSideKnobs              筐体の左右の縁に並ぶレバーのノブ
13 drawCabinetLower           プランジャー帯の装飾+あたりの受け皿

15 drawInsertCoin             insert フェーズのみ
16 drawPlunger
17 drawGiveUpButton
18 drawHandGuide              条件を満たすときのみ
```

**レーンは実線の区間だけを帯として描く。** 穴のところは床が抜けて奥が見える
帯にしてから丸穴を重ねるので、「レーンに開いた口」に見える。
隙間は左右に緑の柱を立て、下へ淡い筒と矢印を描いて「ここから落ちる」を示す。

**レバーのノブは筐体の左右の縁に置く。** 実機ではレバーの軸が側面を貫いて
ノブになっている。走路の端が左・右・左…と交互なので、ノブも交互に並ぶ。
窓枠(13)より後に描いて、枠に載って見えるようにする。

**順序の要点**: コインとパーティクルは窓枠(11)より先に描く。
こうすると盤面からはみ出したものが枠に隠れ、ガラスの内側に収まって見える。

### 8.3 穴の描き方

奥行きが出るように、1つの穴を**手前と奥に分けて**描く。
どちらも `rx` / `ry` の楕円。中央の穴は写真と同じく**丸を隙間なく並べて**開口を埋め、
奥の穴(壁ぎわ)は丸 1 つで描く。

| 関数 | 内容 | 描くタイミング |
|---|---|---|
| `drawOutHoles` | オレンジのリム(下半分を暗く)→ 穴の中(放射グラデーション) | コインより**前** |
| `drawHoleFront` | 手前半分のリング+手前の内壁 | 沈むコインより**後** |

コインが穴に入る瞬間に `drawHoleFront` を重ねることで、
コインの下半分がリムに隠れて「穴の中へ落ちていく」ように見える。

### 8.35 化粧板の絵柄と応援どうぶつをどこに置くか

レーンが盤面をほぼ埋めるので、余白は**走路と走路のあいだ、盤面の中央寄り**しかない。
印刷の草花も応援どうぶつもそこに置く。レーンにも穴にもかからないので、
コースの見通しを損なわない。

## 9. データとストレージ

```ts
interface SaveData { stampCount: number; lastDifficulty: DifficultyId }
SAVE_KEY = 'flickshot.save.v1'
DEFAULT  = { stampCount: 0, lastDifficulty: 'easy' }
```

- **localStorage が使えなくても絶対にクラッシュさせない。**
  Safari のプライベートモードは `getItem` は通るのに `setItem` で例外を投げるため、
  `storage()` は毎回プローブ書き込みで可用性を判定する。使えなければメモリ上だけで動作する。
- 読み込み値は `sanitize()` で必ず検証する(型・有限性・負数・未知の難易度ID)。
- スタンプの種類は `stampIndexFor(nth) = (nth - 1) % ANIMALS.length` で導出。
  カウントだけ保存すれば足りる。
- 保存タイミングは**リザルトに入る瞬間**。演出中にリロードされても記録が残る。

## 12. 検証

### 12.1 `npm run verify`(`scripts/verify-geometry.ts`)

**実際の物理(`src/game/coin.ts`)を回して測る。**
以前、計算上は正しいのに遊べない不具合を何度も作り込んだため。
閉じた式(`successPowerBand`)と実物理の一致も §3 で突き合わせる。

| # | 検査内容 |
|---|---|
| 1 | レーンが盤面 (40..680, 40..994) にコイン半径ぶん余裕を持って収まっている。<br>**レーンがななめ上向き**(高い端の方が上、`dir.y < 0`)。<br>**レバーが画面の左右の端**(盤面幅の 20% 以内)にあり、左右交互。<br>**隙間から落ちた先が手前の穴より低い側**(`landingURange().to < HOLE_NEAR_U`)。<br>投入位置も同様。穴も隙間もコイン直径より広い |
| 2 | 5段のレーンが**すべて同じ形**(長さ・傾き・穴と隙間の位置) |
| 3 | 各操作の成功域を pull 0.05〜1.00 を 0.005 刻みで実シミュレーションして測る<br>・**閉じた式の境界と実物理が一致する**(下限の上下・上限の上で結果が変わる)<br>・成功域が**連続**している(飛び地がない)<br>・**弱すぎでも強すぎでも落ちる**<br>・**空振りが 0 件**<br>・やさしい 60〜100%、ふつう 30〜50%、やさしい > ふつう |
| 4 | 投入後に放置しても落ちない。放置すると 1 段目のレバーで止まって弾ける |
| 5 | どの `power` でも必ず決着する。<br>**最弱でも手前の穴には必ず届く**(空振りのパワー帯が無い) |
| 6 | プランジャー帯 ≤ 25%、盤面とノブが重ならない、指のストロークが画面内、<br>引ききってもノブが画面内、レーンがコインより広い |
| 7 | 全パワー掃引で `u` / `v` が NaN にならず、盤面の外へ出ず、`u` が範囲を外れない |

## 14. 実装時に迷ったら

1. **3歳児が泣かないか。** 迷ったら易しい方・優しい方を選ぶ。
2. **`npm run verify` と `npm test` を通す。** 定数をいじったら必ず両方走らせる。
   「遊べるかどうか」は目視ではなく検算で担保する。
3. **重力は画面の下向き。** 斜面の減速は `GRAVITY * sinθ` として出す(§0.38)。
   進行方向の摩擦に置き換えると、実機と別のゲームになる。
4. **斜面に摩擦を入れない。** 登りと下りが非対称になり、閉じた式(§4.4)が壊れる。
5. **隙間はレーンの高い端の側に置く。** 低い端の側に置くと、落ちた先が手前の穴より
   奥になり、着地したコインが滑り降りる途中で自分から落ちる(§3.2、検算 §12-1)。
6. **空振りを作らない。** `P_MIN` は「最弱でも手前の穴には必ず届く」値より上に。
   弾いても何も起きないパワー帯は、3歳児には理由が分からない(§5.3、検算 §12-5)。
7. **手前の穴を長くするときは隙間が残っているか確認する。**
   `nearHole.to + GAP_LEAD_U` が `GAP_END_U` を越えると成功域が消える。
8. **`LANE_RISE` を上げるときは段が重ならないか確認する。**
   `ROW_GAP > LANE_RISE + LANE_W + LANE_RAIL*2` を保つ(§3.1)。
9. **レーンの形を変えたら §12-2 の均一性と §12-3 の式との一致を必ず見る。**
10. **`P_MIN` / `P_MAX` を手で置かない。** §5.3 の手順で成功域の境界から逆算する。
11. **`src/game/` に Canvas / DOM を持ち込まない。**
12. **外部素材を足さない。** 画像・音・フォント・CDN すべて禁止。
13. これら以外の仕様変更は発注者確認なしに行わない。
